# Pre-Production Security and Readiness Review: SA Harvest CRM

- Review date: 2026-10-01
- Branch / commit: `Development` @ `14803a8`
- Type: read-only audit. No source, config or workflow files were changed. This report is the only file created.
- Inputs read: `.github/copilot-instructions.md`, `docs/DEVELOPER_GUIDE.md`, `README.md`, and the System Design Document (`../Documentation/SA Harvest CRM — System Design Document.md`). The design doc is not in this repository.

---

## 1. Executive summary

The codebase has a lot of deliberate security engineering: account enumeration resistance on login, an atomic single-use public submission token, real PNG structure validation for signatures, short-lived read-only SAS URLs, per-request revalidation of user status and roles against the database, and parameterised SQL everywhere. However, an Admin can take over any SuperAdmin account by changing that account's email and then running the normal forgot-password flow. Login has no brute-force protection, and several production settings are still hardcoded to `localhost` (CORS origin, reset and invite links), so the deployed frontend could not call the API at all. Secrets handling is also not ready: Key Vault and Managed Identity are documented but not wired into the code, the default SuperAdmin is seeded with a password from config and never forced to rotate, and the Docker build context copies the local `.env` into a build layer.

**Verdict: Not ready.** The release blockers in section 3 must be fixed first. Most of them are small, contained changes.

## 3. Release blockers (must fix before production, in priority order)

1. **F-01: Admin to SuperAdmin takeover.** Block non-SuperAdmins from editing or deactivating SuperAdmins (and system users), and revoke sessions when an email changes.
2. **F-03: Hardcoded localhost CORS origin and `Frontend:BaseUrl`.** The production frontend cannot work, and reset/invite links are wrong until this is fixed.
3. **F-02: Login brute-force protection.** Add a strict rate-limit policy and a per-account throttle or lockout on `login` and `reset-password`.
4. **F-12 and F-13: Production secrets and the bootstrap admin.** Wire Key Vault (or App Service Key Vault references) and Managed Identity for Blob storage. Force a password change for the seeded SuperAdmin and for temporary passwords, and refuse to start with the example password.
5. **F-06: Soft-deleted BBBEE certificates and signatures are still downloadable.** This is a POPIA exposure.
6. **F-07 and F-08: Anonymous upload hardening.** Add magic-byte validation, take the client filename out of the blob path, and download as an attachment.

## 6. Positive observations (keep these)

- **Account enumeration resistance on login**: one generic 401, plus a dummy PBKDF2 verification for unknown or inactive users to equalise timing (`LoginCommandHandler.cs:19-57`).
- **Per-request revalidation**: `OnTokenValidated` rejects deactivated users and rebuilds role claims from the database, so deactivations and role changes take effect immediately, not after 60 minutes (`ServiceCollectionExtensions.cs:116-149`).
- **Session revocation on reset and deactivation**: reset-password and deactivation revoke all refresh tokens, and reset tokens are single-use with a 1-hour expiry and 256-bit entropy (`ResetPasswordCommandHandler.cs:43-56`, `SetUserActiveStatusCommandHandler.cs:49-56`).
- **The reset URL cannot be injected**: `ResetPasswordUrl` is built on the server and is not bindable from the request (`ForgotPasswordCommand.cs:6-11`).
- **Public submission token**: 256-bit, 1-hour, claimed atomically and single-use (`UPDATE ... RETURNING`), never the donor GUID (`DonorRepository.cs:73-89`). The public response returns only the `DON-YYYY-NNNNN` reference number and the token.
- **Signature validation**: the size is checked on the encoded length before decoding, the PNG signature is checked, and the IHDR CRC is verified (`Base64PngDecoder.cs`).
- **SAS URLs**: read-only, single-blob scope (`Resource = "b"`), 15-minute expiry hardcoded and not configurable, and no raw blob URL in any DTO (`BlobStorageService.cs:48-57`, `GetDocumentDownloadUrlQueryHandler.cs:13`, `DonorComplianceDto.cs:20-23`).
- **BBBEE download authorisation**: enforced server-side by a resource-based handler, not only by the frontend `RoleGuard` (`DocumentTypeAuthorizationFilter.cs`, `DocumentTypeAuthorizationHandler.cs`). Every controller action has an explicit `[Authorize]` policy or a deliberate `[AllowAnonymous]`. The only anonymous endpoints are login, refresh, forgot-password and reset-password, the two public donor endpoints, the public lookups, `/health`, and the rate-limit test controller (F-22).
- **SQL safety**: all raw SQL is parameterised (`SqlQuery` with interpolation) or built only from integers, and donor sorting uses a whitelist (`DonorRepository.cs:127-143`). No string-built queries were found in reports or export.
- **Export injection safe**: Excel export writes strings as text values with no formulas, so CSV/formula injection does not apply. PDF export uses QuestPDF text runs (`ReportExportService.cs:201-209`).
- **Email HTML injection safe**: staff-composed and public email bodies are HTML-encoded line by line, and the invite link is a fixed, server-built anchor (`SendDonorEmailCommandHandler.cs:100-104`, `SendPublicFormInviteCommandHandler.cs:63-69`, `SubmitPublicDonorCommandHandler.cs:299-303`). Reset email bodies are redacted in `email_logs`.
- **Exception middleware**: a consistent envelope with `traceId`, a generic message for 500s, and stack traces logged but never returned (`ExceptionHandlingMiddleware.cs:111-119`).
- **Swagger**: mapped only in Development (`WebApplicationExtensions.cs:69-76`).
- **Frontend token storage**: memory-only. A grep of the whole frontend found no `localStorage`, `sessionStorage`, IndexedDB or `document.cookie` usage. No `dangerouslySetInnerHTML`. The donor website link is scheme-checked (`DonorOverviewTab.tsx:7-15`). Source maps are not emitted (Vite default). The dev bypass is removed from production builds by the `import.meta.env.DEV` check.
- **Hangfire job safety**: the recurring job uses `[DisableConcurrentExecution]`, is idempotent per task, and is registered with idempotent `AddOrUpdate`, so it is safe across restarts and multiple instances (`TaskDueNotificationJob.cs:15-21,58-67`).
- **Dev data seeding**: gated to Development. The public-form system user is inactive with a discarded random password.
- **Fixed-value fields**: `Status` and `SubmissionSource` are always set by the server on both create paths, and the `income_tax_number` rule exists at the validator and database levels.
- **Secrets in source**: none committed. `.env` is git-ignored and `.env.example` holds only placeholders and the public, well-known Azurite dev key.
